App summary:       
Next generation AI tutor for students, with teacher-designed lesson plans executed by multimodal LLM. 
RAG-based with student progress tracking and adaptive teaching.
Generative UI using Turbo. 2-column layout, allowing the LLM to create visualizations, interactive elements, view media, 
work alongside the student, etc.
Likewise, the student can use the frame as a chalkboard to demonstrate understanding in visual ways beyond plain chat. 
Desktop-only to ensure appropriate interactivity and resource utilization. 
The goal is to match or exceed the tutoring ability of a talented and broadly knowledgeable 1-on-1 human tutor.

dev environment: ruby devcontainer
Intended app environment: containerized, run locally or in a secure environment, not internet accessible

frameworks/tooling:
- ruby on rails 7.2 (plan upgrade to 8)
- security: hosted locally only, up to user to make accessible to internet
- docker containerized + devcontainer
- tailwindcss + shoelace components                                                  
- interactivity - hotwire: turbo, stimulus
- DB: postgres
- active job: solid queue (production only)
- Authentication: devise (upon Rails 8, could remove Devise and switch to the built-in generator and BYO)
- Authorization: User role: student / admin
- LLM servers -  use OpenRouter as it avoids tiered token limits, supports prompt caching and unified API
- LlamaIndex
- RAG: postgres + pgvector + neighbor gem
    https://github.com/ankane/neighbor - ruby gem to use pgvector with rails
    https://www.crunchydata.com/blog/ruby-on-rails-neighbor-gem-for-ai-embeddings
    https://medium.com/@rubyroidlabs/how-to-build-an-ai-chatbot-with-ruby-on-rails-and-chatgpt-9a48f292c37c

Features:
- Separate Teacher and Student interfaces/dashboards
- LLM co-design of lesson plans for teachers in bulk
- Student-progress-aware LLM tutor (RAG-based)
- Multimodal tutoring: 
    - large multipurpose chalkboard frame usable for handwriting, image viewing, generative UI components, iframe for websites, etc.
    - support different levels of multimodality for cost management: allow teacher to set lessons as text (or STT) + image input only, +- speech input, +- realtime API
    - student can respond with either text/voice, chalkboard sketching (rasterize and send as image to LLM), or screenshot of current desktop or webcam view
    - generative UI/mini-apps: GPT to stream components, send with turbo, render either in-chat or on chalkboard frame
      > inline components eg. graphs, charts, maps, etc
      > chalkboard components eg. simulations, games, puzzles, etc.
- automated lesson summary student progress reports

Choosing AI model for lessons:
- at minimum needs text + image input > text + tool use output (use TTS to read aloud responses)
- STT input can be used for most lessons
- audio (speech) input needed for certain types of lessons, eg. music, foreign language, vocal training, speech therapy, emotionally-loaded areas like psychology
 i.e.  ideally audio+text+image input, speech+text+tool output model 
 - might need frontier / reasoning model for advanced lessons in math, physics etc., or for complex generative content e.g. games, simulators
- OpenAI Realtime API speech-speech should not be needed; standard chat API with speech input (turn-based, non-realtime) will suffice
  > would be cost-prohibitive for full days of schooling, without prompt caching
  > future "gpt-4o-mini-realtime" likely cheaper, could be used for basic conversation, early grade levels

prompting principles
- prompt should include anti-screen-time: ensure lessons often include "escape from the computer" moments, suggesting real-world experiments, books, activities, learning outside, resource finding, etc., create hard stops in the lessons to help break up screen time 
- generally avoid testing/quizzing except in single questions as part of a lesson discussion. upon completion of each lesson, generate a summary of student's strengths and weaknesses demonstrated. add to DB. this collection must be embedded for RAG. 
- whenever a resource is used (web page, referenced literature, activity done, etc), add it to the DB archive of utilized resources. 
- Remember: the optimal solution for LLM recall may be full-text keyword search, vector search, a relational database, a graph database, or a mixture.

Turbo notes:
- Turbo Drive intercepts all link clicks and form submissions, making the app SPA by default. 
- Turbo Frames do not contribute support to the usage of Turbo Stream, although they generate an element with ID which can be targeted.
If your application utilizes <turbo-frame> elements for the sake of a <turbo-stream> element, change the <turbo-frame> into another built-in element.
- By default, navigation within a frame will target just that frame. This is true for both following links and submitting forms. 
But navigation can drive the entire page instead of the enclosing frame by setting the target to _top. 
Or it can drive another named frame by setting the target to the ID of that frame.
- GET requests usually would be HTTP requests with a turbo-frame response. if turbo stream needed (eg. within a <tbody>), set data-turbo-stream="true" on links to enable Turbo Stream response.
- Invalid form submissions have to return a 422 status code for Turbo Drive to replace the <body> of the page and display the form errors. 
The alias for the 422 status code in Rails is :unprocessable_entity.
